## 1. Domain Scope and Positioning

### 1.1 Purpose

This document establishes a broad candidate knowledge space for Modern Software Development within the RXI curriculum development initiative.

Its purpose is to identify and organize relevant disciplinary knowledge, concepts, theories, research methods, engineering processes, tools, technologies, artifacts, competencies, and prerequisite relationships.

It is a cognition and reference document, not a finalized syllabus, course specification, or student learning pathway.

The inventory intentionally spans introductory programming, undergraduate computer science, software engineering, advanced engineering practices, and selected emerging research topics. Inclusion in this document does not imply that a topic must be taught to every student.

### 1.2 Domain Definition

Modern Software Development concerns the systematic conception, specification, design, implementation, testing, deployment, operation, evolution, and maintenance of software-intensive products and systems.

It encompasses, but is not limited to:

- Computer science foundations relevant to software construction.
- Programming languages, programming paradigms, and computational problem-solving.
- Software engineering principles and lifecycle practices.
- Web, application, API, and service development.
- Data management and software-system integration.
- Software architecture, quality assurance, security, and reliability.
- Version control, collaboration, automation, and delivery infrastructure.
- AI-assisted software development and agentic development workflows.
- Human, organizational, economic, and ethical dimensions of software engineering.

### 1.3 Boundary with Adjacent Domains

Modern Software Development overlaps substantially with other cognition spaces.

| Adjacent domain | Relationship |
|---|---|
| Applied AI and Intelligent Systems | AI models, inference, intelligent applications, and AI-enabled software systems |
| Human-Computer Interaction, UX, and UI Design | User needs, interaction requirements, usability, interface implementation, and evaluation |
| Business Intelligence and Analytics | Data pipelines, analytical applications, reporting systems, and decision-support tools |
| Robotics | Embedded software, control software, middleware, and hardware-software integration |
| Industrial Design and Engineering | Digital product realization, connected products, simulation, and engineering software |
| Foundation Core | Systems thinking, mathematics, computational reasoning, scientific inquiry, and technical communication |
| Advanced Core | Systems architecture, abstraction, modeling, integration, verification, and complex problem-solving |

These boundaries are organizational aids rather than strict disciplinary separations. A single project may involve multiple domains simultaneously.

## 9. D8 — Levels and Prerequisites

The levels below are provisional observation categories. They are not equivalent to formal academic years, and they should not be used as direct placement labels for students.

### Level A — Introductory Familiarity

Candidate capabilities:

- Explain what software and programs are
- Represent a simple problem as a sequence of steps
- Write small programs using variables, conditions, and loops
- Use basic functions and data structures
- Recognize inputs, outputs, and errors
- Understand files, folders, and simple command-line operations
- Explain the purpose of source control
- Build or modify a small working artifact

### Level B — Foundational Application

Candidate capabilities:

- Decompose moderately complex problems
- Use functions, modules, and basic abstractions
- Apply introductory data structures and algorithms
- Work with a programming language's development environment
- Use Git for basic version control
- Write and run automated unit tests
- Build simple web or data-driven applications
- Read documentation and debug unfamiliar code
- Explain basic design and implementation decisions

### Level C — Integrated Engineering Practice

Candidate capabilities:

- Design a multi-module application
- Define and consume APIs
- Integrate a persistence layer
- Apply modularity and separation of concerns
- Use testing beyond simple happy-path cases
- Collaborate through repository workflows
- Build and deploy an end-to-end prototype
- Evaluate design alternatives against constraints
- Use AI coding assistance with independent verification

### Level D — Advanced Engineering and Specialization

Candidate capabilities:

- Evaluate architecture and quality attributes
- Design maintainable systems with explicit contracts
- Apply systematic testing and debugging
- Understand concurrency and distributed-system trade-offs
- Establish automated build and delivery pipelines
- Analyze security, performance, and reliability
- Evaluate AI-assisted development workflows
- Conduct evidence-based technical comparisons
- Produce a documented and reproducible engineering project

### Level E — Graduate-Level or Emerging Research

Candidate topics and capabilities:

- Formal methods and advanced verification
- Programming language implementation and semantics
- Advanced software architecture and evolution
- Distributed systems research
- Empirical software engineering
- Automated program analysis and repair
- AI for software engineering
- Evaluation of agentic development systems
- Human-AI collaboration research
- Reproducible experiments and critical research synthesis

**Important:** Level E is included for domain coverage and future reference. Its presence does not imply that advanced research topics are appropriate for the target students or current delivery model.

### 9.1 Candidate Prerequisite Relationships

Potential prerequisite chains include:

- Computational reasoning → programming fundamentals → data structures and algorithms
- Programming fundamentals → modular programming → software design
- Programming fundamentals → web fundamentals → frontend or backend development
- Programming fundamentals → SQL and data modeling → data-driven applications
- Programming fundamentals → automated testing → continuous integration
- Git fundamentals → collaborative development → code review and release workflows
- Requirements analysis → system modeling → architecture and implementation
- Application development → deployment fundamentals → monitoring and maintenance
- Testing fundamentals → systematic verification → advanced quality assurance
- Programming and debugging → AI-assisted coding → agentic development with verification
- Basic networking → APIs and services → distributed-system concepts

These chains are provisional. Actual prerequisites depend on the selected language, toolchain, project, and learning objectives.

## 11. Coverage Audit and Selection Readiness

Before this cognition space is used to derive course content, conduct the following audits.

### 11.1 Coverage Audit

- Are the principal computer science foundations represented?
- Are programming, software engineering, and application development distinguished?
- Are requirements, architecture, implementation, testing, deployment, and maintenance covered?
- Are data, networking, security, and distributed systems represented?
- Are modern collaboration and delivery practices covered?
- Are AI-assisted and agentic development treated as emerging engineering practices rather than replacements for software fundamentals?
- Are research methods and evaluation approaches represented?
- Are socio-technical and professional dimensions included?

### 11.2 Classification Audit

- Are disciplines distinguished from concepts, methods, tools, artifacts, and competencies?
- Are programming languages and frameworks treated as examples rather than entire knowledge domains?
- Are workflow methods distinguished from lifecycle phases?
- Are testing techniques distinguished from testing tools?
- Are architecture concepts distinguished from architecture deliverables?
- Are competencies expressed as observable capabilities where possible?
- Are research topics marked as candidates rather than established curricular requirements?

### 11.3 Duplication and Granularity Audit

- Identify concepts repeated across multiple sections.
- Determine whether repetition reflects genuine cross-domain relevance or unnecessary duplication.
- Avoid mixing broad disciplines with overly specific tool features at the same hierarchy level.
- Keep examples separate from stable conceptual categories where appropriate.
- Avoid assuming that every item belongs to exactly one category.

### 11.4 Relationship Audit

- Identify important prerequisites and dependencies.
- Identify concepts shared with HCI, AI, robotics, analytics, and the core models.
- Record relationships that should be reused across cognition-space documents.
- Distinguish prerequisite relationships from project-based integration opportunities.

### 11.5 Selection Readiness

The inventory can support course selection only after candidate topics have been evaluated against:

- Target student profile and prior knowledge
- Intended learning outcomes
- Course duration and instructional hours
- Available equipment, software, and instructional support
- Project feasibility and assessment methods
- Institutional delivery constraints
- Safety, privacy, and licensing considerations
- Desired level of disciplinary authenticity
- Evidence of learning and demonstrable student outputs

No topic should be included in a course merely because it appears in this inventory.

## 13. Status and Next-Step Boundary

This document is a broad candidate inventory for the Modern Software Development cognition space.

It does not yet define:

- The final curriculum structure
- The final Foundation Core or Advanced Core content
- The learning outcomes of an individual course
- The order in which students must study all topics
- The final programming language or framework stack
- The required level of AI-assisted or agentic development
- The final assessment and portfolio requirements

The next appropriate step is a coverage and classification audit, followed by a selective mapping of relevant concepts to the overall curriculum cognition space.

Course-level selection and implementation should occur only after the relevant cognition baseline has been reviewed and sufficiently stabilized.
